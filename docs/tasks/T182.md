# T182 Split the slowest test modules so the gate's jobs balance

- **Kind**: tooling (tests)
- **Issue**: #585 · **Branch**: `task/T182-split-slow-modules` · **Merge after**: none
- **Evidence**:
  - [designed: owner, 2026-11-04: "but cannot you split those dumb tests"; "yes do it"] The gate and CI wall time is
    set by a few long modules: the gate runs whole modules in parallel (`tools/check_premerge.py`, `GOAL2_GATE_JOBS`,
    #567), so one 25-minute module is the floor whatever the job count.
  - The main session's gate of T180 at 6807e201 (Linux, slow tests included): `test_watched_adapter` 1502 s,
    `test_core_round_t108` 1083 s, `test_watched_publication` 998 s, `test_ui_match_day_t167` 884 s,
    `test_campaign_competitive_save` 699 s, `test_watch_qualifiers_t176` 682 s, `test_watched_save` 597 s,
    `test_campaign_competitive_match` 597 s, `test_watched_pitch_jobs` 596 s, `test_ui_bench_t180` 553 s.
  - Slow modules are chosen per change by `tools/slow_reach.py`; a split module must stay reachable from every change
    that reached the original (the gate's own layout test, `test_premerge_layout_t145`, and `test_premerge_jobs_567`).
  - #565: on a loaded runner, the port's wall-clock dispatch limit fails a reference match. Shorter modules spread the
    load; this task does not change the limit.
- **Owns**: the modules it splits (new `goal2/tests/test_*.py` files beside them), any shared helper moved to a
  `goal2/tests/*_cases.py` module, `tools/slow_reach.py` only to keep the reach, `docs/process.md` §10 if a number
  there changes.
- **Scope**: the claim protected: **every check that ran before runs after, unchanged; only the module boundaries
  move.**
  1. For each module over 400 s in the list above, find its independent expensive set-ups (a `setUpClass` that plays
     a match day, a class per case, subTests over cases that each play a match). Split along those: one new module per
     independent set-up or case group, so that no module repeats an expensive set-up another already pays.
  2. A module whose tests all share one set-up (one match played once, then many assertions) is not split: splitting
     it would play the match twice. List these, with the set-up's time.
  3. Moving code only: no assertion, case, seed or reference changes. Helpers shared by physically moved classes go to a
     `*_cases.py` module imported by each. Alternatively, keep the shared bodies in the original guarded
     `test_*.py` module and use `load_tests` entry points to select independent groups. [designed: main session,
     2026-11-04] This preserves `SLOW_PATHS` for test-body edits and existing helper imports/globals; unguarded
     shared sources would lose automatic slow validation.
  4. Keep `slow_reach.py`'s reach: every change that reached the old module reaches each part.
- **Done when**:
  1. The test inventory is unchanged: the set of `(test id without module name, assertion count)` collected before
     and after is equal. A small script in the PR body shows it (collected with `unittest`'s loader, and `ast`
     counting `self.assert*` calls per test).
  2. Each new module passes on its own, run one at a time (`GOAL2_SLOW=1` where the old one needed it).
  3. The main session's gate, before and after, on the same machine with the same `GOAL2_GATE_JOBS`: the PR reports
     both wall times and the longest module of each. The longest module after is shorter than before.
  4. `test_premerge_layout_t145` and `test_premerge_jobs_567` pass; a change to a file the old module was reached
     from still selects every part (shown for two such files).
  5. **Do not run `tools/check_premerge.py`.** The main session runs gates one at a time (process.md §10). Then CI:
     Windows and Linux green, except `test_core_replay_t140` (#520).
- **Review**: none.
- **Hazards**:
  - **Losing a test.** The inventory check (Done-when 1) is the guard; a missing test is a failure, not a cleanup.
  - **Doubling a set-up.** Splitting a module whose tests share one set-up makes the gate slower, not faster.
  - **Machine load.** Run your modules one at a time, never the whole suite.
