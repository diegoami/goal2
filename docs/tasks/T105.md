- **Scope**:
  - **The driver** (`goal2/core/driver.py`).
    - `Driver(core)` takes the player one screen to another by the original's own keys: `goto(kind)` from the manager menu, and back with Esc.
    - Every key it sends must be one the current kind accepts (G9's table). It refuses anything else, and it never presses a key a screen doesn't list.
    - A screen it does not expect stops it with the kind, site and text. It never guesses.
    - It is deterministic: the same calls give the same key log.
  - **The views** (`goal2/core/views.py`). These are pure readers of the core's memory through the kit's `Image`:
    - the manager's desk: manager name, team, rankings, next opponent and the fixture kind, and the managers;
    - the fixture list: every fixture of the current stage with its kind, sides, mark, played flag and score;
    - the tournament: group tables, or the bracket when the original keeps it;
    - the history: past winners and records.

    Each field cites its address from the annotated globals or the listings. A value the original computes only on display is read by visiting that screen through the driver, and the reason is stated.
  - **The desktop.** `python3 -m goal2.desktop --core <savestate> --data <GOAL.DAT> [--save <core save>]` (and `--resume <core save>`) opens the main window on a `CoreModel`. It gives the Country page and the Fixtures page the same data shapes the current `DesktopModel` gives them. Those pages show the views on the fixed page.
    - Routes the core cannot serve yet (Team edits, Pool, play) are shown disabled, with the G task that brings them. They never fall back to the Python route.
    - Save (F7 in the original; the Save page here) writes the core save. Resume replays it.
  - The current Python route (`--template`) is unchanged.

- **Hazards**:
  - Never parse the text page for a value the desktop shows. The text is only the oracle in tests.
  - Never write a byte into the core's memory, and never press a key a screen does not list.
  - Don't reach into the Python route's `GameState` from the core route. The two models are separate.
