# T229 Publish a release from a green Package run's own ZIP

- **Kind**: infrastructure (release; v0.1)
- **Issue**: #705 · **Branch**: the session's `claude/…` branch in a cloud session, locally `task/T229-release` ·
  **Merge after**: T228
- **Why**: [designed: owner, 2026-11-13, #705; T225 item 6] v0.1.0 is published with the ZIP of the green package
  run on `main`. The cloud session cannot fetch that artifact: its storage host is denied by the network policy and
  changes between requests (`productionresultssa8`, then `sa11`, `.blob.core.windows.net`), and the allowlist takes
  exact hosts only.
- **Owns**: `.github/workflows/release.yml`, `docs/packaging.md`'s release paragraph.
- **Scope**: the task protects one claim: **a release attaches exactly the ZIP a green Package run on `main` built and
  smoked, at that run's commit.** A manual workflow takes the run id, the tag and the notes file; it refuses a run that
  is not the Package workflow's successful push to `main`, re-runs `check-zip` on the ZIP, refuses an existing tag,
  and creates the release at the run's commit with the ZIP and its SHA-256.

## Done when

1. The workflow is on `main` and, dispatched with a run id that is not a green Package run on `main`, refuses before
   publishing (shown on a run of it).
2. Dispatched with run 43470121366 (Package on `main` f869e1d8, green), tag `v0.1.0` and `docs/releases/v0.1.0.md`, it
   publishes the release with `goal2-0.1.0-win64.zip` and `SHA256SUMS.txt`, tagged at f869e1d8.
