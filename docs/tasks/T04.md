# T04 The 12 skills: derived from three record bytes (+4, +5, +7) via the class and profile tables

- **Kind**: slice
- **Issue**: #<new>
  **Branch**: `task/T04-twelve-skills` · **Merge after**: T03
- **Implementer**: the main session
- **Reviewer**: `luna` (the derivation is a static analysis of F008's listing traces, not an engine seam; the lighter reviewer fits)
- **Evidence**: F008 (the player screen's 12 skills, behavioral across 80 player screens E007-r0009..r0012). The formula is `DS:6DCD[12·(+5) + c] · ((+4) + 1) div 256` with `c = DS:6D25[12·(+7) + i]`. The class table (14 positions × 12 rows) is at `DS:6D25`; the profile table (16 profiles × 12 classes, values 5..26) is at `DS:6DCD`. Both are in the savestate's data segment (`DS:6D20..6EB3`, 404 bytes). The fidelity oracle is E007's published player screens on archaeology's E007 release.
- **Owns**: `goal2/engine/skills.py` (the derivation, the data tables, the bar computation), `goal2/tests/test_skills.py` (the table-loading test, the derivation test, the E007 fidelity test).
- **Scope**:
  1. The data tables: load the 14×12 class table from `DS:6D25` and the 16×12 profile table from `DS:6DCD` in the savestate's data segment. These are initialised data, not in the 20-byte player record.
  2. The derivation: `skills(record) -> list[int]` returns 12 bar lengths (0..25), one per skill in the order F008 names: keeping, kicking, tackling, heading, marking, passing, crossing, feinting, control, dribbling, shooting, penalties. `goal kicking` is NOT shown (F008: the template holds the name `kicking` once and `goal kicking` nowhere; the 12 shown are the 13 in `GOAL.HLP` without `goal kicking`).
  3. The bar computation: `bar = profile_value · ((+4) + 1) div 256`. The max is `26 · 254 div 256 = 25` (F008). Seen range: 3..25 over 80 players.
  4. The fidelity test: downloads E007-r0009's player screens, parses the 12 bar lengths per player (the 0x70 cells in each of the 12 skill rows), and asserts every bar matches. The test skips with the reason when the fetch fails.
- **Done when**:
  1. `python3 -m unittest goal2.tests.test_skills` is green against the released GOAL.DAT and the E007-r0009 player screens (skipped with the reason when either is absent).
  2. The fidelity test compares all 12 bars of all 80 players in E007-r0009..r0012 against the model's output; 0 mismatches.
  3. `python3 -c "from goal2.engine import skills; r = bytes(20); print(skills.skills(r))"` prints 12 zeros (the all-zero record's skills are all zero because the profile index is 0 and the class index is 0).
- **Hazards**:
  - never commit a savestate (rule 19); `.cache/` is git-ignored; the test downloads from `gh release download E007`;
  - the data tables are at fixed offsets in the savestate's data segment; a wrong offset silently gives wrong skills (F008: the tables are 404 bytes at `DS:6D20..6EB3`);
  - the bar formula is `div 256` (integer division by 256), not `div 255` or `div 254`; a wrong divisor changes every bar;
  - the 12 skills are in the order F008 names; `goal kicking` is the 13th in `GOAL.HLP` but not on screen; the model returns 12 values, not 13;
  - the class table is indexed by `+7` (position, 0..13), not `+6`; F008: "+7, not +6, feeds height, foot and the skills";
  - the profile table is indexed by `+5` (profile 1..16); a zero `+5` (the all-zero record) gives the first profile's values, which may not be all zero.
