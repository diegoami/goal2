# T222 Boot the core from the player's own GOAL.EXE

- **Kind**: feature (the core's third entry kind; v0.1's first task)
- **Issue**: #705 · **Branch**: in a cloud session the session's `claude/…` branch, locally `task/T222-exe-boot` ·
  **Merge after**: —
- **Why**: [designed: owner, 2026-11-13, #705] v0.1 ships the core route with the player supplying their own GOAL.EXE
  and GOAL.DAT. Today the core's new game starts from `e039-r0005-date-call.sav`, an emulator state recorded with
  GOAL.EXE in memory (`Core.boot`, docs/core.md "The new game"). A player cannot produce it, and it never ships
  (CLAUDE.md rule 14).
- **Evidence**:
  - [confirmed: `goal2/engine/original_match/build.py:3`] The registered GOAL.EXE: packed SHA-256
    `a6928b0bb7cda0303ac8daf8690efc56ef1792dddaccb5c6f3d85af1f68d3664`. Its MZ header: LZEXE 0.91 (`LZ91` at
    offset 28), no relocation entries, entry `000E:15F1`, stack `2DE7:0080`, 2 header paragraphs.
  - [derived: feasibility probe, main session 2026-11-13, #705] Loaded at segment `0823` (the load segment of
    every E039 state) in a bare 1 MiB machine, with an `int n; iret` stub behind each vector, the program
    unpacks itself and reaches the date call `235C:0071` (AH 2Ah) in under a second. On the way it asks for:
    INT 21h 35h ×18, 25h ×5, 44h ×1; INT 10h 0Fh ×2, 1130h ×1, 08h ×1, 02h ×2 (the last two through Turbo
    Pascal's `Intr`); and it reads the BIOS tick at `0040:006C` (the CRT unit's delay calibration).
  - [derived: the same probe] Its **whole load module** (code and initialised data, 92,359 bytes from the load
    segment) equals `e039-r0005-date-call.sav`'s **byte for byte**. Of the program's memory above it, 114 bytes
    differ: DS:7B4A (the CRT delay count), DS:AAAF–AABC (CRT variables set from the unanswered INT 10h 08h and
    1130h), DS:86CC–86DB and DS:ACC0–AD07 (interrupt vectors the program saved, which point into DOSBox-X's
    BIOS in the recording), and stack words at SS:3DF2 and SS:3FCD–3FE1. Outside it: the IVT, the BIOS data
    area, DOS's memory blocks, the PSP, the screen and the ROM. These causes are hypotheses until the task
    shows each.
- **Owns**: a new module `goal2/core/exeboot.py` (or an entry in `runner.py`; the implementer chooses and says
  why); its test `goal2/tests/test_core_exe_boot_t222.py`; `goal2/desktop/data_setup.py`'s MANIFEST and the
  desktop's first-run boot; `docs/core.md`'s "The new game" section; `docs/packaging.md`'s "The player's data
  folder".
- **Scope**: the task protects one claim: **a new game booted from the player's GOAL.EXE is the same game as one
  booted from the recorded date-call state.**
  1. Build the date-call core from GOAL.EXE's bytes alone: a minimal DOS (IVT, BIOS data area, an MCB named
     GOAL, a PSP, an environment), the load module at segment `0823`, run from the MZ entry and serve only the
     requests above, as DOS and a VGA BIOS answer them. Anything else stops with `InterruptError`, as the
     core's rule is: it never guesses.
  2. Answer the BIOS so the program's own memory comes out as the recording's: the attribute and character
     at the cursor, the font information, the tick rate that gives the recording's delay count. Where a value
     cannot be produced so (a saved vector into the BIOS), name it in a table in the test and in
     `docs/core.md`, with why the game never reads it before quitting.
  3. Refuse a GOAL.EXE of another SHA-256 before running it, naming the file.
  4. The desktop's default start and the first-run import ask for **GOAL.EXE and GOAL.DAT**, not the recorded
     state. `--core-boot <recorded state>` keeps working for developers and the existing tests.
  5. No byte of GOAL.EXE or of the recording enters the repository: the tests read them from `.cache/` and skip,
     naming the file, when it is absent.

## Done when

   date call, the booted core's load module equals `e039-r0005-date-call.sav`'s, and its DS and live stack
   (SS:SP up to the stack's top) equal the recording's except the named table of item 2, every entry of which
   the test checks by address.
2. From both starts, the same new game (`title_key="n"`, `Driver.new_game(7, "bob")`, DOS time 10:00:20.95) for
   **both** E039 dates (1990-10-04 and 1992's) reaches the manager menu with equal DS, seeds DS:7B62/7B64,
   country and player arrays, and the same waits, kinds and screens on the way. T106's E039 manager-menu
   comparisons pass from the GOAL.EXE start too.
3. Under `GOAL2_SLOW=1`: the first watched match of that new game, played by the same keys from both starts,
   gives the same result and the same DS at full time.
4. A GOAL.EXE of another digest is refused with a message naming it, before any instruction runs.
5. `goal2.tests.test_first_run_t153` passes, amended so the import takes GOAL.EXE and GOAL.DAT (a folder with

- **Hazards**:
  - **Equal in the load module is not equal in the game.** Item 2 of Done-when is the claim; the load module
    is only where it starts. Do not stop at the date call.
  - **Do not copy bytes out of the recording to make the memory match.** Every byte of the booted core must
    come from GOAL.EXE, from DOS/BIOS answers the task documents, or from the program's own run. A value
    lifted from the recording (the delay count, a vector) is a recording shipped by another name.
  - **The tick is an input, like the date.** If the delay count depends on it, make the rate the documented
    one that gives the recording's count, and say so with `[derived]`; never write DS:7B4A directly.
  - The core's interrupt rule (docs/core.md "Refusals") holds after the date call unchanged: the boot's DOS
    answers serve only the boot.
