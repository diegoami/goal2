# T02 The new game's data: GOAL.DAT, the country/manager/player/squad tables

- **Kind**: slice
- **Issue**: #7 ·
  **Branch**: `task/T02-goaldat-loader` · **Merge after**: T01
- **Implementer**: the main session (goal2 runs thin-process until it has surface for the harness)
- **Reviewer**: `luna` (harness.json `reviewer.default`; the work is data-shape, not an engine seam, so the lighter reviewer fits)
- **Evidence**: goal2-archaeology's `static/goal-dat/blocks.tsv` (the block table) and
  `tools/static/goaldat.py` (the block-shape checker) on `GOAL.DAT` at
  sha256 `bc5e5c04434d31f350eb7803afc3810333393e049d50dde559797a5b068c60ca` (44,040 bytes).
  F002 (R001–R011) is the static inventory; the file ships as an archaeology release
  asset (`goal2-original` release on goal2-archaeology, or from the `E006` evidence
  bundles as `e006-1000-r0001/game/GOAL.DAT`).
- **Owns**: `goal2/data/` (the data directory, never a vendored file), `goal2/data/goaldat.py`
  (the loader), `goal2/tests/test_goaldat.py` (loader tests). Vendored engine files
  (T01) are read-only.
- **Scope**:
  1. The package's data: `goal2/data/__init__.py`, `goal2/data/goaldat.py` — a loader
     that reads `GOAL.DAT` (sha256-pinned) and exposes ten blocks (country names,
     player names, player initials, manager names, manager initials, four per-country
     arrays, the squad-20 array) as Python objects. The block offsets and sizes are
     the loader's, from `static/goal-dat/blocks.tsv` (R001 in F002).
  2. The `GOAL.DAT` asset: a fixture the loader can read in tests. The data file is
     not committed (rule 19): it is fetched from `goal2-archaeology`'s `goal2-original`
     release by sha256, into `.cache/`. The fetch happens in tests on demand; missing
     data skips the test with the reason.
  3. The loader's invariants: each of R001–R011 from F002 holds for the data file
     (block sizes; country names in records 1..128; player names in records 1..3060;
     initials 0..3060 are upper-case ASCII; manager records 1..128 plus 6 zero
     records 129..134; the three per-country arrays; the two per-country permutations;
     the squad-20 array). Each invariant has a one-line test that runs against the
     loaded data.
  4. A `tools/check_goaldat.py` script: `python3 tools/check_goaldat.py <path to GOAL.DAT>`
     exits 0 when every check passes, non-zero otherwise. Mirrors the archaeology's
     `tools/static/goaldat.py`; the library form (`goal2.data.goaldat.run_checks(data)`)
     is what the script calls.
  Out of scope: making players (T03); the 12 skills (T04); the country record's runtime
  fields like the world rank (F002 O5) — T02 covers the data, T03 wires the runtime.
- **Done when**:
  1. `python3 -m unittest goal2.tests.test_goaldat` is green against the released
     `GOAL.DAT` (skipped with the reason when `.cache/GOAL.DAT` is absent).
  2. `python3 -m goal2.data --check <path to GOAL.DAT>` prints the R001–R011 check rows
     and exits 0; a truncated file fails R001 with a non-zero exit (regression in the
     test).
  3. `python3 -c "from goal2.data import goaldat; d = goaldat.load(open('.cache/GOAL.DAT',
     'rb').read()); print(d.country_names[1], d.player_names[1], d.squad_20[1])"`
     prints the country name, the first player name, and the squad-20 array for
     country 1, in that order. The PR's fenced block shows it.
- **Hazards**:
  - never commit `GOAL.DAT` (rule 19; the data file is an asset of goal2-archaeology's
    releases only);
  - the loader must be byte-exact on the block offsets and sizes (R001); an off-by-one
    in the offsets would silently pass R001 but fail R002 onwards. The tests check
    R001..R011 individually, so a partial drift is caught;
  - the data file's SHA256 must match the loader's pinned value (F002 R001: 44040
    bytes, sha256 `bc5e…60ca`); a wrong file fails with a clear error;
  - the per-country permutations (R009, R010) read as the loader expects; an
    end-of-array check guards against an off-by-one in the read;
  - the player names block is the largest (33,671 bytes; 11 bytes per record × 3061).
    Reading it all at once is fine; the test asserts the last record (3060) is the
    Pascal string the rest of the data expects.
