- **Evidence**:

  - T01 (the vendored quick engine): `quick_engine.simulate(state)` returns a `dict` with `score`, `goals`, and the two seed words (`seed_DS7B62`, `seed_DS8336`).
  - T06 (state adapter): `goal2.engine.savestate.Savestate(path)` opens a DOSBox-X savestate and exposes the memory layout the engine reads.
  - E006 (archaeology): `e006-1000-r0001` is the published main-screen savestate; the half-time savestate from E006 is the engine's primary input. T14 reuses it.
  - T12 / T13 (state): T14 reads `state.starting_eleven` (for the chosen eleven label) and `state.captain` (for the captain marker) but **does not feed them into the engine** — the vendored engine reads the original memory layout, not the rebuild's state. The screen labels itself "STAND-IN" so the user knows the result reflects the chosen savestate, not their choices.
- **Owns**: `goal2/ui/result.py` (the screen); `goal2/tests/test_result.py`
- **Scope**:
  - The result screen (`goal2.ui.result.run_result`):
    - Signature: `run_result(savestate_path: str, keys: Iterable[Key] | None, *, state: GameState | None = None) -> bool`
    - Returns `True` on Enter (continue to next fixture), `False` on Esc.
    - On call: loads `savestate_path` via `goal2.engine.savestate.Savestate`, runs `goal2.engine.quick_engine.simulate(state)`. The vendored engine is at `goal2/engine/quick_engine.py` (vendored, not edited — CLAUDE.md rule 18).
    - The screen never mutates `state`. Esc and Enter return without writing. [designed: T14 is read-only with respect to the rebuild's state adapter; the engine result is the screen's data, not state.]
    - When `keys` is `None`, the screen calls `read_key()` in a loop (T11's pattern). When provided, it iterates scripted keys (the test surface).
    - The `savestate_path` is the test's argument; the screen does not look up the file. A real caller (the main loop, future task) supplies it.
  - Rendering (the test surface):
    - Title row 0: `RESULT  STAND-IN`. [designed: the stand-in disclaimer is the screen's contract]
    - Row 1: blank.
    - Row 2: `FINAL SCORE  H-A` where H and A are the engine's `result["score"]` (e.g. `(1, 0)` → `FINAL SCORE  1-0`). [confirmed: the engine's `score` is a 2-tuple of ints]
    - Row 3: blank.
    - Rows 4..4+N-1 (one row per goal): ` MM  team T  scorer P` where MM is the minute (1..46 per A-MATCH-0), T is the goal's team (0 or 1), and P is the scorer's player record (per `result["goals"][i]["player"]`; rendered as `chr(player_record_byte)` via CP437, since the engine's player field is the byte at `+0` of the scorer record). [designed: the byte→character render is what the original screen showed; a digit doesn't work for non-ASCII player initials like `P SCHMEICHEL`'s `P`]
    - If there are no goals (0-0): rows 4..4 are a single `  no goals` row. [designed]
    - After the goals list: a blank row, then `SEED DS:7B62  0xNNNN  DS:8336  0xNNNN` (the engine's two RNG outputs). [confirmed: the CLI prints these; T14 follows the same format]
    - Footer row 24: `ENTER CONTINUE  ESC QUIT`. [designed]
    - The body rows' content is computed from the engine result, not from `state`. The screen's `state` argument is accepted for API parity with T11/T12/T13 (so the main loop can pass a single `state` through every screen) but unused by the rendering.
  - Out of scope: **reading `state.starting_eleven` / `state.captain` / `state.country_tactics` to label the lineup that "would have" played** — a follow-up task (the stand-in disclaimer already tells the user the lineup was not applied). **A result-on-failure path** (the engine raises `FoulPathNotModelled` or `ExtraTimeNotModelled` per T01) — a follow-up; v1 catches them and returns `False` with a single-line `REFUSED: <message>` rendered on row 2 in lieu of the score. The test in Done-when 5 covers this case.
- **Done when**:
  1. `python -m unittest goal2.tests.test_result` is green.
  2. `test_result` skips with the reason when the savestate file is absent (T09 used this pattern with `_dat_path()`; T14 follows it — fetch from `goal2-archaeology`'s `goal2-original` release if `gh` is logged in, otherwise skip).
  3. With a fixture savestate that the engine produces a known result for (T14 uses the E006 half-time savestate T01 was tested against), `run_result(savestate_path, [ENTER], state=state)` returns `True` and the rendered title row is `RESULT  STAND-IN`. The score row's content is `f"FINAL SCORE  {score[0]}-{score[1]}"` where `score` is the engine's `result["score"]`. The expected score is computed from running the engine once in the test (not hardcoded) — so deleting the engine call leaves no row 2 content.
  4. With the same fixture, `run_result(savestate_path, [ESC], state=state)` returns `False` (state passed for API parity, no field asserted because T14 doesn't mutate state).
  5. The refusal path: with a fixture savestate that the engine refuses (the T01 foul-path test fixture), `run_result` returns `False` and row 2 contains `REFUSED: <substring of the engine's exception message>`. The exact substring is computed from the engine's exception type, not hardcoded.
  6. The render surface test calls a private `_render(savestate_path) -> Grid` (the engine runs once inside the helper, and the result is rendered). Asserts:
     - Title row 0 starts with `RESULT  STAND-IN`.
     - Row 2 contains `FINAL SCORE  ` followed by the score tuple's elements joined by `-` (computed from the engine's result).
     - If `result["goals"]` is non-empty, rows 4..4+N-1 each contain `team ` and `player ` substrings (the engine's goal dict keys).
- **Hazards**:
  - "Test passes with the grid deleted" (lesson from T05/T09/T10/T11/T12/T13 review rounds): the expected score and goals are computed from the engine's result, not hardcoded — so deleting the engine call leaves empty rows and the test fails.
  - "Engine is not called" — T14 must call `quick_engine.simulate(state)` once per `run_result` invocation. The mutation test: deleting the engine call makes Done-when 3, 4, 5 fail (no score, no goals, no refusal message).
  - "Score format is hardcoded" — the test asserts `f"FINAL SCORE  {score[0]}-{score[1]}"` with both elements from the engine's tuple. Hardcoding `FINAL SCORE  1-0` would pass for one savestate and fail for a different one; the test uses a fixture with a known result (T01 used `E006-r0001`'s half-time savestate; the engine's score is recorded in T01's test output).
  - "Engine refusal is silent" — Done-when 5 ensures `FoulPathNotModelled` / `ExtraTimeNotModelled` are surfaced. Without the try/except, the screen raises and the test fails.
  - "Goal rows format off-by-one" — row 2 is the score; row 4 is the first goal; row 24 is the footer. With N goals, rows 4..3+N are goals. A test with 0 goals asserts the `no goals` row at row 4. A test with N goals asserts row 3+N is a blank row before the seed words.
  - "Savestate file path is hardcoded" — the path is passed as an argument; T14 doesn't look up a default. Tests pass the fixture path explicitly; a missing path is the test's responsibility (skip pattern).
  - "Vendored engine file is edited" — CLAUDE.md rule 18. T14 reads `goal2.engine.quick_engine` via its public API; it does not edit the vendored file. The PR diff should not touch `goal2/engine/quick_engine.py` or `goal2/engine/savestate.py`.
