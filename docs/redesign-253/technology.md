# Desktop technology and migration decision

[designed: #253] **Recommend retaining the Python backend and PySide6 Widgets for the first Country desk delivery, with the accepted SDL viewer boundary intact.** This is a proposed technology recommendation, not an immutable requirement or migration authorization. It serves the information-heavy management experience with the most reusable validated behavior. Qt Quick is the strongest alternative if the owner prioritizes a single rendered visual system and accepts additional view/automation work. Tauri/Electron remain credible desktop alternatives; neither means browser-only delivery. The parity matrix and journeys do not depend on selecting one.

## What actually constrains the backend

[confirmed: code3335da83; PROVENANCE.md] `goal2/engine/` contains pinned vendored Python models and the optional original-match kit; modifying it is prohibited by repository rules. The game uses Python state/campaign/eligibility/management adapters, both RNG words and guest Memory/VGA continuity. Original execution uses the accepted kit and Unicorn; the schematic viewer consumes ordered causal samples rather than running its own simulation. [State](../../goal2/game/state.py), [desktop model](../../goal2/desktop/model.py), [watched publication](../../goal2/game/watched_publication.py), [controller](../../goal2/desktop/watched.py) and [provenance](../../PROVENANCE.md) establish these boundaries.

[confirmed: session_save.py3335da83] Persistence is a versioned explicit JSON rebuild session containing complete records/state, RNG, campaign/result data and the embedded template. Accepted versions distinguish legacy friendly/campaign/watched content. The writer replaces atomically; resume validates a detached complete candidate before publishing. This is not .GL compatibility, a generic database or a remote session API. Future UI work should reuse the writer/loader; a new frontend does not justify replacing save format or reinitializing player records.

[confirmed: DesktopModel source3335da83] `DesktopModel` is Qt-free and calls Python game/state/save interfaces. Qt owns widgets/publication; workers own match computation on copied candidates; the viewer has read-only presentation packets. Event/frame order, consumed-tail publication, real paint acknowledgements, cancellation/owned-child cleanup and no concurrent save/edit are accepted constraints. T85 changes presentation pacing under its own contract. The retained web server exposes a subset of old gameplay routes; it is not a complete supported service boundary for the whole campaign.

[derived: those separations] Python is a strong cost/fidelity requirement in practice, but not a mathematical necessity. A different frontend can call Python in-process or through a rigorously bounded local process adapter. Porting the backend to Rust/C#/GDScript/JavaScript would require reimplementing record/domain rules, exact RNG/continuation/persistence, kit integration and all fidelity evidence, with independent equivalence checks. No current player task or measured backend bottleneck justifies that expense. Keep the backend, with an owner decision required for any exception.

## Proposed decision and validation boundary

[designed: #253] Approve the experience direction first, then B01 establishes a bounded proof before production work commits to a toolkit/packager: real20/80-player tables with T84's expanded columns and complete cards;900×640 and1440×900 logical clients at actual1x/2x; keyboard-only selection/confirm/error/scroll behavior; supported match sample playback/real paint acknowledgement; clean cancel/focus/return; a native package run on Windows and Linux without developer checkout/Python installation. Include resource acquisition/verification, save location, upgrade/rollback and unavailable native dependency states. Preserve current launchers/saves throughout the proof.

[designed] Record cold launch, steady memory/CPU and renderer behavior for the **same scenario/resources** on the same target machines, without claiming a universal winner. Proposed feasibility budgets: no long synchronous work on the UI thread, responsive input/cancel, no lost/reordered accepted samples, bounded queues and complete continuation equivalence. Agree numeric responsiveness/resource budgets after actual baseline measurements, not invented package-size claims. Screen-reader checks must cover table names/headers/selection, complete card, errors and match-event summary; native accessibility APIs alone are not acceptance.

[designed] If Widgets/SDL meets those tests, proceed with the recommended retention path and coordinated window presentation. If a single-window requirement is selected or retention fails a concrete task, compare a bounded Qt Quick version of the **same** scenario; bring evidence and an explicit migration choice to the owner. Tauri/Electron/Godot are options for an owner-selected change in maintenance/visual priorities, not silent fallbacks. No experimental prototype or dependency migration is executed under #253; B01 and every implementation child wait for explicit direction approval.
