## What native hooks actually support

[confirmed: v2.0.28 primary source] plugin/hooks.ts:66–96 registers callbacks in append order and runs them sequentially on the SAME mutable event. No protected priority/finalizer/veto API exists. plugin.ts:127–146 registers plugins in setup order. plugin/supervisor.ts:99–102 orders native pre, external packages, native post. Native ConfigPolicy post hook (config/plugin/policy.ts:48–62) can only set deny. Searching all111 audited native source files found no other permission.hook registration and no native shell create.before registration.

[confirmed: v2.0.28 primary source] permission.ts:164–190 returns explicit configured deny before any hooks, then combines saved grants, then invokes permission.evaluate. A guard can tighten allow to ask after saved grants; it must never turn ask/deny into allow. The public plugin PermissionDomain (plugin/src/{promise,effect}/permission.ts) exposes hook/list/get/reply only, not ask/assert. Therefore it cannot issue a new native external_directory request through the supported public API. It CAN force the existing shell request to ask, which native noninteractive run answers reject with feedback. Such a receipt must truthfully say shell permission rejected due to external-directory compatibility checking, not fabricate an external_directory event.

[confirmed: v2.0.28 primary source] tool execute.before receives tool/session/agent/message/call identity plus mutable input; execute.after supplies the same identity. Only before has a typed Tool.Error failure channel. Shell create.before is later than tool.before and precedes native shell preparation; it has command/cwd/shell/env, but NO session/call identity or permission-assert API. Thus a before-hook-only scan is insufficient when arbitrary shell-mutating plugins remain enabled.

## Prevent other hooks overriding the guard

[confirmed: native config/plugin/source.ts:127–159; plugin/supervisor.ts:27–55] Auto-discovery operations come before configured operations, and trusted CONTENT document is last (config.ts:263–269). Plugins config supports remove selectors -* and exact IDs. Wildcard removal disables every non-guarded plugin; guarded native IDs are opencode.provider.opencode and opencode.config.policy. Exact additions re-enable matching definitions. Config plugin operations are reapplied on reload; a one-time inventory check is therefore NOT sufficient protection.

[designed] Apply a trusted plugin activation allowlist in the final overlay: remove all with -*, re-enable exact expected native builtin IDs needed for the normal baseline, then add the trusted guard directory. Do NOT re-enable opencode.* or *, which could re-enable arbitrary external IDs. Pin builtin source identities and expected active inventory; preserve intentional baseline native disables rather than indiscriminately enabling optional builtins. Require exactly the expected guard id/source/hash/active state, expected native inventory and no unknown/failed/duplicate entries before billing. Use a per-run unique guard ID to avoid accidental namespace collisions, and validate source rather than ID alone. Recheck inventory/readiness for runtime changes; any unexpected activation fails closed/cancels ONLY this owned execution. Native hot reload keeps the last content overlay allowlist, so later global additions cannot ordinarily become active hooks.

[designed/limitation] Normal global providers configuration remains loaded; builtin ConfigProvider and native credential service remain enabled and the same isolated v2 login DB remains unchanged. Compare safe selected/custom-provider catalogue projections to baseline. External global auth/provider plugins cannot be preserved arbitrarily while simultaneously promising their hooks cannot override policy: these are executable same-process code. If the selected provider needs one, STOP before billing and report it for explicit audit/pinning; do not silently drop it, narrow the catalogue or substitute routing. Native hook/config APIs do not offer capability isolation between provider/auth and permission/shell hooks. The proposed allowlist is a policy restriction on active plugins, not protection against malicious arbitrary host code executed during module import. No OS-jail claim.
